# RandySkills 🎣

Randy 的專屬 AI 助手技能庫 (Agent Skills)。

目前收錄 **3 個 Skill**：

| Skill | 做什麼 |
|---|---|
| [**rod-spec-decrypter**](#釣竿盲狙解碼矩陣-rod-spec-decrypter) | 分析單一竿款：反推調性、手感、感度 |
| [**rod-tech-splitter**](#技術搭載拆分器-rod-tech-splitter) | 建檔工具：把官方系列技術清單拆到各型號 |
| [**rod-curve-generator**](#彎曲曲線產生器-rod-curve-generator) | 把分析報告畫成受力彎曲曲線圖 |

**職責嚴格分離**——第一個只讀資料、不寫字典；第二個只做歸屬判定、不碰手感分析；第三個只吃前者的報告、不自行推導規格。

---

### 釣竿盲狙解碼矩陣 (Rod Spec Decrypter)
無視官方型錄的行銷修辭，從釣竿的物理幾何與材質資料反推真實調性與手感。

- **嚴格獨立分析**：每支竿獨立推演，禁止拿其他竿款交叉比對腦補。
- **動態載入廠牌字典**：技術名詞與型號命名規則都採「精準比對」，查無資料時明確揭露「不在字典庫中」，**絕不臆測**。
- **型號自動解碼**：依廠牌命名字典逐欄位拆解型號字串（長度／繼數／力量／調性／種類／機能後綴／年份）。
  ⚠️ DAIWA **把調性標在型號裡，不在規格表裡**——規格表沒有獨立的 action 欄位，這是正常的。真正的風險在於原廠會不定期塞進**沒公佈定義的字元或修飾符**（如 `722MLRSS-24` 多出來的 `S`），那些只能靠推論，Skill 會強制標為回推並附上理由與證偽判準，不會混充成原廠定義。
- **錐度診斷**：內附 Python 腳本計算幾何錐度比，並主動示警兩點式比值的已知失效情況。
- **感度鏈路判定**：把訊號從餌傳到手拆成五個環節（竿先／導環／blank／接繼／輪座），**串聯系統取最差的一環**當結論，不加總也不平均。
  ⚠️ 感度**沒有官方標示可以對答案**——調性判定敢下結論是因為型號字串裡就寫著原廠標的調性（`F`／`R`／`S`）可以對，感度沒有這種東西。所以 Skill **不輸出任何分數**，只講兩件不需要對答案就成立的事：**卡在哪一環**、**什麼線組條件下才感覺得出來**。全段強制標為推論。
- **資料來源分級**：一律**先查官方**。只有官方確實沒有該欄位的項目（如導環圈材質）才准動用零售商規格頁，且必須標 🟡 並註明出處。
  ⚠️ **搜尋引擎的摘要不算來源**，必須實際讀到規格頁；只拿到摘要就標「未確認」。評測、開箱、使用感一律不採用——**不論它出現在哪個網站，包含官方網站上的行銷文案**。
- **自動產出報告**：於當前目錄輸出 Markdown 分析報告。
- **白話書寫**：報告以**國中生看得懂**為標準。外文術語保留原文並加註（`胴調子（slow taper）`、`SVF COMPILE-X（碳纖維排得密所以又輕又硬）`），數字後面一定緊接「這代表什麼」。
  ⚠️ 白話化**只改變講法，不改變內容**——可信度標示一律保留，而且講得更直白：「這是原廠寫的」／「這是我推的」／「**這是猜的**」。
- **反直覺的原理必須配比喻**：判準很直接——**一句話寫完的物理原理，如果「看得懂的人本來就已經懂了」，那就等於沒寫**。這類原理一律要配日常比喻：線的弓形用**拉繩子**、訊號鏈用**被壓扁的水管**。章節內第一次用到的內部簡寫（`粗細比`、`元端過剩指數` 等）也必須**就地解釋**——報告很長，不能要求讀者往回翻。
  🔴 **不准自創代稱**：型號裡的 `F`／`R`／`S` 就是原廠標的調性本身，直接寫「原廠標的調性是 `R`」，不要包裝成「調性字母」；訊號鏈的五個環節也不准簡稱「五環」——「環」是導環的名字，簡稱等於用零件名指代整條鏈。
  🔴 **不畫 ASCII 圖，一張都不畫。** 文字加比喻已經足以讓國中生看懂，所以不需要判斷「這裡該不該畫」——答案一律是不畫。想畫圖的衝動代表的是**文字還沒講清楚**，回去把文字寫好。
  ⚠️ 比喻是為了建立畫面，**不是**讓不確定的結論聽起來更肯定；比喻本身若屬推論，一樣標 🟡。

### 技術搭載拆分器 (Rod Tech Splitter)

廠牌官方產品頁的技術區塊是**整個系列共用**的：一份清單列出所有技術，再用小字 ※ 標註哪些只適用於部分型號。本 Skill 把這份共用清單還原成**每一支竿各自的搭載明細**。

- **標註規則**：無 ※ ＝ 系列通用｜`※A、Bのみ` ＝ 限定｜`※A除く` ＝ 排除。型號採精準比對，全形半形須先正規化。
- **衝突消解**：同部位互斥時，有 ※ 標註者優先於無標註者（如 `X45` 擠掉通用的 `X45フルシールド`）；跨部位則並存（實心竿先接管狀本體不算矛盾）。
- **三重交叉驗證**：拆分結果須與**各竿官方介紹文**、**型號字串後綴**、**規格數值**三者對照，全部對得上才算完成。對不上時**停止並回報矛盾**，不自行選邊。
- **可信度誠實**：搭載事實有**三層來源**——①官方 ※ 標註 🟢｜②**該機種官方介紹文直接寫出技術名稱** 🟢｜③「無標註 ＝ 全部搭載」的規則推論 🟡。
  ⚠️ 第 ② 層最容易被漏掉而誤降為 🟡，那是**低報證據強度**——原廠明明寫在該機種頁面上，卻被說成「這是我推的」；反過來把第 ③ 層寫成 🟢 則是虛報。**兩個方向都會讓可信度標示失去意義。**
  ⚠️ 但只有寫出**技術名稱本身**才算第 ② 層。「細身肉厚のチューブラーブランク」是**描述**，不等於寫出了 `TUBULAR POWER SLIM`——不嚴格區分，這一層會蔓延到行銷修辭上。

🔴 **它只回答「這支竿有哪些技術」，不解釋技術的物理影響、也不做手感分析。** 產出寫進 `<廠牌>_<系列>_features.md`，供 `rod-spec-decrypter` 讀取。

### 握把長度量測器 (Rod Grip Measurer)

當原廠規格表**沒有**グリップ長這一欄時，改由**官方商品圖**量出握把長度與**可利用竿長**（全長 − 握把）。

**方法的關鍵是「圖裡自帶一把尺」**：官方商品圖多數是拆成兩節平放，而**元節的像素長度就對應官方公佈的仕舞寸法**。不需要知道相機參數。

- 🔴 **Step −1 不可跳過**：先確認原廠是不是根本就有這個欄位。有就用官方值（🟢），不要用量測值（🟡）去取代它。「DAIWA Heartland 沒有這一欄」是已核對過的事實，**不是通則**。
- 🔴 **量不出來是合法結局，不准推測**。拿不到圖／切出 ≥3 條帶／握把佔比落在 10〜25% 之外，一律失敗且**不輸出任何數值**。三種結局要分開講：「原廠從未定義」／「資料在別處」／「查無此資料」。
- 🔴 **嚴禁用公式回填**：同樣 218cm 的六支，握把差 **10.7cm**；最好的規則 RMS 仍有 1.94cm。這是逐支資料，不是規則。
- **三道防線**：導環會造成單點厚度尖峰（曾把一支量成 96.5cm，真值 34.5），所以握把前緣必須「連續超過 1.2% 節長」；數值須通過合理性檢查；寫進量測表後會**自己再讀一次複查，不對就回滾**。
- 🔴 **複驗圖是唯一的人工把關點**，必須實際看過——數字合理不代表位置抓對。
- **回歸測試**：`validate_grips.py` 拿 12 張官方圖重量一次比對答案卷，誤差須 < 1.0cm。目前 12/12 通過，最大誤差 0.04cm。

### 彎曲曲線產生器 (Rod Curve Generator)

把 `rod-spec-decrypter` 產出的 `<型號>_分析報告.md` 讀回來，用大撓度懸臂梁解算器算出受力彎曲曲線並繪圖（柔度 ∝ $1/d^4$，⚠️ 該指數是**實測擬合出的有效值**，非物理推導）。**檔名是兩個 skill 之間的契約。**

- **雙模產圖**：`plot-zenaq`（45 度持竿的等比例形狀圖）與 `plot-engineering`（水平持竿的分析圖，上下兩面板分開畫「額定區間」與「深彎」）。兩者**共用同一組負載與同一套物理**，差別只在持竿角度。
- **負載跟著竿子走**：額定區依該竿的路亞負載推演；**深彎點**畫到**竿尖下沉全長 1/3**（CCS 標準深度）。洩力上限（`適合ライン上限 lb × 453.6 × 1/3`）仍會算出來印在圖上，但**不繪製**——那個負載會把竿子推到形狀退化、各竿差異被壓平、甚至模型非單調的區域。
- **跨竿對比圖用「各自基準」**：`shape`——每支都彎到竿尖下沉全長 1/3，深度統一後純比形狀。固定絕對負載對混著 L 到 H 的一組竿並不公平，而且結果只是在重述力量字母。
- **形狀有校準，公分數沒有**：形狀對照 21 支公佈 CCS Action Angle 的空白竿身（RMS 4.5°）；絕對撓曲量逐支散佈 ×/÷ 1.32，**不得拿去對照實測**。
  ⚠️ **CCS 校的是竿尖角，不是「彎在哪一段」。** 曲率分佈只有一份實物照片量測（`722MLRSS-24`）：引擎的彎偏元端約 3〜6% 竿長。n=1，只當方向參考。
- **握把段不參與彎曲**：固定端是手不是竿尾。握把長度由 `rod-grip-measurer` 從官方商品圖量出（27.3〜43.2cm），收在 `references/measured_grip_lengths.md`。沒量過的竿款會警告並標「未量測」，不套用剛性。
  ⚠️ 舊版圖上的握把灰帶／黑棒是寫死的猜測值且從不進物理，已改成同一個量測值既畫也算。
  🔴 **實物彎曲照片要先篩透視壓縮再比。** 那張照片沿竿身被壓縮約 4 倍——看起來是又深又漂亮的大弧，實際只有 9〜10% 的竿尖下沉。快篩與量法見 `references/ccs_calibration.md` §10。
  ⚠️ 工程圖的 y 軸有縮放，所以圖上會印出**垂直放大倍率**，每條曲線也標「佔全長多少 %」——沒有這兩樣，額定上限那 2〜3% 的撓曲會被誤讀成「這支竿工作負載下就把彈力耗光了」。
- **不替任何欄位填預設值**：缺**全長／先径・元径／ルアー重量**的報告會被列為失敗並以 exit code 1 結束；其餘欄位缺漏時圖上顯示「報告未提供」，不顯示成看起來像規格的數字。
- **材質與技術只印報告載明者**，原廠調性四碼 `S`／`R`／`F`／`X` 原樣保留；圖上的 `[Model Parameters]` 已標明是繪圖用推估值。
- ⚠️ 需要 `uv`（外部相依，不隨本 repo 安裝）。

**丟非 Daiwa 的竿子進去會怎樣？** 不會亂編，但能力會明顯降級：

- ❌ **無法自動解碼型號** —— 各廠牌命名規則互不相同（長度編碼、力量字母、後綴含義皆異），沒有字典就不得憑印象拆解。AI 會直接揭露「該廠牌的命名字典尚未建立」。
- ❌ **無法解析技術名詞** —— 找不到技術字典時，該廠牌的碳布等級與專利技術一律標示為「不在字典庫中」，不推導任何物理影響。
- ✅ **幾何推演仍可運作** —— 只要你提供先徑／元徑／全長／負載，錐度運算與失效診斷照常執行。
- ⚠️ **報告會標示「可信程度降低」**，說明結論僅建立在幾何之上。

換句話說：**非 Daiwa 竿款可以用，但你會拿到一份只有幾何、沒有材質疊加的分析。** 想要完整支援請比照 [擴充其他廠牌](#擴充其他廠牌) 建立字典。

## 💡 使用方式

安裝完成後直接在對話中呼叫：

> 「請幫我用釣竿解碼矩陣分析 Daiwa HL 722MHRB-19，先徑 1.8、元徑 11.8、全長 2.18m、負載 7〜21g」

AI 會自動載入廠牌字典、拆解型號、呼叫 Python 腳本完成幾何運算，並產出報告。

**提供的規格越完整，推演可信度越高。** 每個欄位各自解鎖不同的判定：

| 你給的欄位 | 解鎖什麼 |
|---|---|
| 先徑／元徑 | 錐度比（最低要求） |
| ＋ 全長、負載**上限** | 錐度腳本的兩項進階診斷（元端過剩、全體纖細⁽¹⁾） |
| ＋ 負載**下限** | 荷重讀取窗——這支竿的重量感落在哪一段餌重 |
| ＋ 継数、仕舞寸法 | 接繼位置（官方若有 `ジョイント仕様` 欄則優先採用） |
| ＋ カーボン含有率 | blank 內有無非碳的高阻尼材料 |
| ＋ **適合ライン** | 洩力上限⁽²⁾——圖上會標示，但不繪製（理由見註） |

省略等同於放棄該項判定，而缺漏的環會被標成「未知」並影響感度結論。

> ⁽¹⁾ 🔴 **「全體纖細」只降級距，不改變彎曲點。** 元徑很細代表**絕對剛度低**——很輕的負載就彎得很深；
> 它**不代表**「整支一起彎」。**軟**（要花多少力氣）與**彎在哪**（形狀）是兩條獨立的軸，一支竿可以同時很軟又很前調。
> 這條規則有官方背書：`702UL+FS-ST23` 元徑僅 7.4mm、比值 10.57，**原廠仍標 `F`**。

> ⁽²⁾ 🔴 **竿子承受的持續拉力上限由洩力決定，不由魚的大小決定。** 張力一超過洩力設定，線就被放出去。
> 而洩力不可能高過線的破斷強度，慣例設在 1/3 → `洩力上限 = 適合ライン上限(lb) × 453.6 × 1/3`。
> 🟡 1/3 是釣魚圈慣例，非原廠規格。
> ⚠️ **但曲線不畫到那裡**——那個負載會把竿子壓到撓曲 45〜71%，形狀退化成「直段＋垂直尾」、
> 12 支的竿尖角全部收斂到 ~90°（看不出 F 和 R）、再高模型還會非單調。
> 圖上畫的是**竿尖下沉 1/3 全長**（CCS 標準深度）。細節見 `rod-curve-generator` 的 README。

`bin/install.js` 是**掃目錄自動發現** skill 的（認 `SKILL.md` 的存在），新增 skill 不必改安裝腳本。但 SKILL.md 裡呼叫腳本的路徑**必須寫成 `<skill_dir>/scripts/...`**——安裝時會被替換成絕對路徑，寫裸檔名的話注入到 Copilot／Cursor／Windsurf 後會找不到腳本。

**三份參考檔的分工是刻意切開的**，混用會造成 context 污染：

| 檔案 | 存什麼 | 載入時機 |
|---|---|---|
| `<廠牌>_technology.md` | **技術是什麼意思**（物理影響） | 必載 |
| `<廠牌>_model_naming.md` | **型號字串怎麼拆**（命名文法） | 必載 |
| `<廠牌>_<系列>_features.md` | **這一支竿是什麼**（搭載技術、官方數值） | **僅當 prompt 指名該系列** |

🔴 技術字典**不得登錄任何型號或搭載清單**——否則分析 A 系列時會把 B 系列的型號一起帶進 context。機種級事實一律隔離在系列專屬的 features 檔裡，該檔只在需要時才載入。

### 擴充其他廠牌

新增廠牌需要在 `references/` 下建立**兩份必要字典**，Skill 會依廠牌自動載入：

```
references/<廠牌>_technology.md      # 技術名詞 → 物理影響
references/<廠牌>_model_naming.md    # 型號字串 → 規格欄位
```

**選用**（有查證資料再建，可由 `rod-tech-splitter` 產出）：

```
references/<廠牌>_<系列>_features.md  # 該系列各型號的搭載技術與官方規格數值
```

請比照 `daiwa_*.md` 的格式撰寫，並為每個條目標註可信度：

- 🟢 **官方明文定義** —— 原廠文件直接載明。請一併附上出處連結與原文引用；若該文件屬**其他系列**，須註明套用至本系列屬推論。
- 🟡 **由官方文案回推** —— 從原廠敘述的語境推導而來。標為 🟡 者，AI 在報告中**必須**說明其為回推結果，不得當作原廠公佈的事實。
- ⚠️ **併存的競爭假說** —— 同一欄位存在其他尚未被排除的合理解讀時，一併記錄「目前採用哪一個」「不採用的理由」與「證偽判準」。

> 🔴 撰寫「不採用的理由」時，**不得使用循環論證**——例如以「該欄位已被 X 佔用」來排除 X 以外的解讀，因為欄位歸屬正是待證的結論本身。理由必須不預設拆解結果即可獨立成立。

## 🛠️ 開發須知

**Skill 的唯一真實來源是本 repo。**

安裝腳本會**整包覆寫**目標目錄，因此直接修改 `~/.claude/skills/` 或 `~/.gemini/config/skills/` 底下的副本，會在下次安裝時被無聲蓋掉。

正確流程：

```bash
# 1. 改本 repo 的檔案
# 2. 重新部署
node bin/install.js -g
```

> 📌 `package.json` 的 `version` 刻意維持 `1.0.0`。目前只從 GitHub 安裝，`npx` 一律取預設分支的 HEAD，
> version 不 gate 任何行為。日後要發佈到 npm registry 時再開始 bump。
